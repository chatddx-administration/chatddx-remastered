# Agent instructions

This document contains project-wide instructions written by humans for agents.

## Environment

- `set -a; . ./.env-container; set +a`.
- `store` uses PostgreSQL 16:
  - pg_ident.conf: chatddx <os-user> chatddx / chatddx <os-user> chatddx_writer
  - pg_hba.conf: local all all peer map=chatddx
  - Setup database and roles with `src/chatddx/store/setup.sql`
- Base the fake vLLM on 0.24.0, extend/amend continuously as new facts are discovered, questions arise or sample data is
  needed.
- `pnpm --dir frontend build` builds frontend.
- `chatddx.settings` is the project-wide source of truth.

## Handling errors and warnings

How to handle a warning or error:

### 0. Ignore

Consider not handling an error if:

- it's out of scope
- its timing, fallout and message are about right

### 1. Crash at boot

First choice: If a runtime error can be known at boot

1. write a check that crashes it at boot
2. attach a "fix boot-check <boot-check>" message should it occur at runtime

### 2. Raw writes to stderr and/or edges

These are for developers and ops, so:

- minimize tampering with the message
- maximize simplicity in handling.

### 3. Inform UX runtime

Tell user:

- what's going on
- what they can do now

## Testing

### Python

```
AGENT: rewrite
"Baseline" now names the check before work starts (see "Workflow"), and `pytest` skips the browser tests.
---
- `pytest` runs every test but the browser tests, in ~110s.
```

- Baseline is `pytest` runs every test and takes ~110s;
- `pytest -m 'not slow'` takes ~22s.
- `pytest -n 4` runs the baseline in ~70s, the quick run gains nothing from it.
- Names tests share (models, endpoints, the recipes most tests run, the cases) are spelled once, in
  `src/chatddx/test/world.py`.

### TypeScript

- `pnpm --dir frontend test` tests frontend takes less than 2s

### Browser

- `scripts/check.sh browser` builds the frontend for them first.
- `pytest -m browser` runs the browser tests that `pytest` skips, in ~75s

### Nix

Agents aren't expected to run this, just know it exists.

`nix flake check` runs:

- `scripts/check.sh`'s docs, package and frontend stages
- `nix/test.nix` boots the NixOS module in a VM for its test, takes ~7 minutes
- `nix/module-eval.nix`

## Workflow

The workflow is a session's: it starts from a human-reviewed commit, and ends with a handover the human asks for. What
the session commits in between is its own, and is squashed.

### 1. Before work starts

On a fresh commit, run `scripts/check.sh baseline`, on non-zero exit, pause work and relay the flags.

### 2. Between units of work

No rules: use your own judgement and the tests and checks at your disposal (see "Testing"), such as a package's tests,
`pytest -m 'not slow'` or `scripts/check.sh docs`. Commit and push as you see fit, a session's hooks may ask for both at
a turn's end but neither is a handover.

### 3. Handing over

Only when the human asks for the work, or for a pull request:

1. Remove all comments and docstrings that don't pass doc rule 3 and 4 respectively (pre-existing included).
2. Run `scripts/check.sh`, which checks what the branch changed since it left `origin/main`, then tell the human of each
   `flag:` it prints, and flip what the budget suggests when it feels right.
3. Commit and push, and open the pull request if one was asked for.

## Development stages

A thing under development is in one of the following stages:

1. Felt - Not really anywhere but still present somehow
2. Implied - Seen only when looking for it
3. Mentioned - Expressed as a concrete need
4. Named - Greppable and referred to as `<name>`
5. Itemized - Has one or more items in `docs/backlog.md`
6. Planned - Has a concept of a plan in `agents/plan-<name>.md`
7. Drafted - Exists as a moving target in code and `agents/wip-<name>.md`
8. Solidified:
   - Docs under rule 1 in `docs/modules/<name>.md`
   - Surface stamped in `docs/surfaces/<name>.md`
9. Cemented: TBD
10. Protected: TBD

Things can bounce around freely across these stages but is only in one stage at a time. Docs are never moved and
reworked in the same commit:

- when entering rule 1: Rework -> commit -> move -> commit -> insert suggestions.
- when leaving rule 1: Move -> commit -> rework.
- when moving within rule 1: Move -> commit -> insert suggestions.

## Documentation rules

### 1. Humans write, agents suggest.

In all docs, except `agents/*` and stage change moves, agents are only allowed to insert suggestions.

A suggestion is inserted as a fenced code-block immediately above the subject to change. The backticks are part of the
template, use 4 backticks as envelope if the suggestion contains a code-block.

```
AGENT: <verb>
<short explanation>
---
<optional suggestion for new content>
```

`docs/surfaces/*` is generated by `chatddx stamp` and is stamped by a human when a public surface changes.

### 2. Docs refer to the code, the code speaks for itself.

The primary document is `docs/chatddx.md`: If a contradiction to it is discovered, stop, describe the landscape and
provide options.

- The module-scoped documentation is in `docs/modules/<module>.md`.
- The doc may refer to code `concepts` or direct file reference `src/chatddx/file.py:Class.prop`.
- References from code to docs are never allowed.

### 3. When and how to write a comment.

- A) Every line of comment imposes a readability tax.
- B) A future reader can be saved work by knowing about non-evident details.
- When B is considerable enough to offset A, a comment is justified.

1. Prefix with the comment's nature (e.g. Patch, Compromise, Prototype, "Accommodating for a discovered fact")
2. Tell what's non-evident and only what the code doesn't already tell, example:

```python
# Optimization: Reusing families' language reduces query-load.
def _languages_of(self, cases: Sequence[str]) -> dict[str, str | None]:
    known = {c: f.about.language for f in self.families() for c in f.cases}
    if rest := [c for c in cases if c not in known]:
        known |= languages_of(self.rows, rest)
    return {c: known[c] for c in cases}
```

3. Optional: Use links. If a section of code is related to another section of code elsewhere such that reading both make
   them easier to understand, insert links between them along with the comment. Example:

```python
# Policy: De facto refusal mechanism for
# src/chatddx/runner/score.py:judge_at and src/chatddx/bench/seen.py:Seen.at
def serving(
    self,
    digest: str,
    serves: Callable[[str], str | None] | None = None,
    called: str | None = None,
) -> str:
    # ...
```

### 4. When and how to write a docstring

Public solidified entry points may have a docstring that describes their cost and utility. The cost is the resources it
invokes, locks it holds and complexity of its operations. The utility is derived from its responsibilty without any
assumptions about the caller.

It should be written as a direct continuation of its signature, raises and findings and only fill in the blanks:

- A) Every line of docstring imposes a readability tax.
- B) Callers can dodge reading the source if the docstring gives them the right idea.
- When B outweighs A, a docstring by that amount is justified.

Docstrings are reported by `chatddx stamp` for a stamp.

### 5. Don't reference branch commits

They'll be squashed.

### 6. Placeholder username

- For placeholder usernames in docs and tests, use
  1. alice, bob, carol...
  2. semantic names (archive, guest, nobody, other, collaborator-one, admin).
